# Relay design — human-controlled sharing

## Decisions before this revision (section 15)
1. Principals are Ava, Priya, Ben, one agent per team, and an explicit demo operator. Clearance is team-level: isolation is between teams, not between people on one team. Personal chat routes additionally enforce ownership.
2. Bitmasks: shared=0, eng=1, sales=2. `server/store/visibility.ts` is the sole SQL gateway for events, chunks and search. All callers supply a server-resolved principal.
3. One chat per person/channel with that team's central agent; one shared thread per account/topic. Shared human posts are explicitly confirmed, not private chat.
4. Delivery cursors belong to (channel, team), advance only on validated digest delivery, and carry the last included merge SHA and sequence.
5. Shipped means merged to the default branch and labeled customer-facing. These GitHub sources are registered public inputs, not declassifications of private engineering conversations.
6. Every private-to-shared transition is an explicit human action: rep confirms a staged escalation; engineer confirms document text or approves an answer/update. No auto-release path. Agent and MCP tokens cannot perform human actions. Declassification writes a private audit plus a separate shared record; originals remain immutable.
7. Structured, citation-validated replies default to needs_escalation (Sales) or insufficient_context (Engineering). An unknown Sales answer only stages a confirm card; no Engineering job starts before a click.
8. High-risk dates, prices, discounts, SLAs, availability and commitments use placeholders in Engineering drafts. Humans replace them or explicitly choose none committed. The server rejects unresolved placeholders and configurable internal terms. Sales-facing claims must match cited released evidence; private Sales deadlines may answer the person's own internal question but cannot establish a product commitment or leave the team without confirmation.
9. FTS5 filters masks and BM25-ranks within one SQL query, top six and about 1,500 tokens. Retractions exclude sources before ranking and from every context-building path.
10. Per-audience summaries every twelve messages, union of input labels. Retraction invalidates summaries and derived messages referencing withdrawn records, transitively, for future context; already-delivered history remains visible with a notice.
11. Five drafts per question. Each shared answer reveals a bound; authorized human disclosure and paraphrased gradual leakage remain residual risks.
12. Untrusted text is JSON encoded inside explicit delimiters. Tools close over fixed principals. Seeded injection text cannot grant permissions or approve anything.
13. AGENT_MODE=rules is deterministic/offline; AGENT_MODE=llm uses Anthropic and requires a key. Unset defaults to rules. One transient retry, then a clear failure; live GitHub errors explicitly fall back to fixtures. Logging stores prompt text only when LOG_PROMPTS=true.
14. Serial queues per conversation; SQLite AUTOINCREMENT event ordering; SSE resume by Last-Event-ID. A single Node process serves this demo.
15. Branching/carry-over cut. No transcript copying between audiences.
16. Docs/repo conflicts cut; citation labels identify source provenance for human review.

## Policy details and assumptions
- Demo identity selection issues human UI tokens. MCP uses separate scoped tokens derived by the client transport boundary; their principal.kind is agent and their token scope is mcp. Even if used against REST, they cannot escalate, approve, release, retract, post shared human messages, or reset. No approval/release tools exist.
- A date supplied by a human can be approved even when not previously published. A model must not fabricate one. Engineering drafts are normalized to placeholders and retain high_risk_fields; UI controls and server validation both enforce resolution. Configurable INTERNAL_TERMS defaults to Basalt and CANARY-ENG-7F3A.
- Explicit demo controls simulate a public GitHub merge and reset the demo. They require UI human tokens, never a model tool. Reset is append-only logical retirement of prior channel records and reseeding a new active demo channel; no event deletion and no running-database unlink. Historical events remain inspectable to authorized principals.
- Retraction cannot unsend a delivered message. A new append-only event marks the source withdrawn; source lineage removes derived content from future retrieval/context, including released document chunks. Users may still read their historical transcript with a withdrawn notice.
- Documents preserve original_text separately from overlapping chunks, so release confirmation hashes exact uploaded bytes. Shared copies retain that exact text and independent chunks.
- Rules-mode private Sales questions may cite the requesting team's private note (e.g. Northwind signing condition). Product answers remain sourced from released context. Engineering returns insufficient_context for the signing question.
- The three-column /demo uses independently authenticated Sales chat and Engineering chat, with a shared middle thread and engineer approvals. The operator table is displayed only with ?operator=1 and explicitly shows full-clearance visibility. It is a demo control, not production authentication.
- Light/dark mode, shared posts, document upload and release, explicit escalation cancellation, rejection and retraction are part of the vertical slice. Two-person approval is a stretch and is not exposed in the UI.
- No deployment, real authentication, tenant isolation, PDF, embeddings, branching, mobile-specific product, or billing. Existing Anthropic model defaults are task-specified and require account verification; local SDK mocks verify mechanics, not real account availability.


## Product redesign assessment (2026-10-17)
Baseline after pulling existing remote evaluation work: 25 tests pass, 24/24 seeded cases pass, TypeScript check passes. Preserve Express, SQLite/WAL/FTS5, the visibility gateway, scoped agent tools, validated replies, exact-text human approval, documents, GitHub fixtures/digests, SSE, MCP, export and retraction. No rewrite or new dependency is warranted.

Gaps to close: outputs are scattered between thread/documents/releases; version and approval history are hard to find; source inspection is authorized but unaudited; demo operator issuance is unauthenticated; attack evaluation uses a stale unscoped MCP token; usefulness metrics are absent. Implement a permission-filtered artifact projection over existing events/documents/releases, an artifact library, inspection audit entries, reviewer-only operator exchange, and evaluation/reporting improvements. Do not introduce a generic artifact storage system or executable runtime. A document version is an upload with the same name within a channel; recipients count only versions visible to them, so private revisions do not leak through version numbers. Answers/updates are immutable independent artifacts (v1); revisions are new releases, not silent edits.

Relay is a shared knowledge and artifact workspace. Engineering-to-Sales is the first workflow. Buyers (Sales Engineering/Product Operations leads at smaller B2B software companies), urgency, pricing, and ROI remain hypotheses. Interview five prospective users about repeated technical questions, existing handoffs, approval authority, sources of truth, failure costs, and budget ownership. Pilot one account for a week against a preceding week: questions answered without Engineering, cited-answer correctness, unsupported claims, escalation rate, reviewer minutes and edits per release, median response time, and repeat questions. Time saved and willingness to pay are not measured by this demo. Record review time manually in the pilot; do not infer it from model latency.

Read clearance and release authority remain separate. Artifacts expose only permitted sources/history; sharing an approved output never grants source access. Inspection audit logs store principal, action and identifier, not source text. Prompt logging remains off by default; evaluation enables it only in an ephemeral database. Demo identity switching and reviewer-to-operator exchange are convenience controls, not production authentication. Production needs verified identity, tenant/channel ACLs, server-managed reviewer assignments, connector secret management, durable queues, audit retention/access policies, rate limits, and independent security review.

Scanner matching is defense in depth: paraphrases and gradual disclosures can evade fingerprints; authorized humans can release sensitive content. Prompt injection remains an adversarial input even with fixed tool permissions. Team-level clearance does not isolate colleagues on the same team. Passing seeded tests demonstrates tested behavior, not semantic non-disclosure or production security.

Future small-software artifacts are design-only. Generated code must run in a disposable isolated sandbox with no inherited agent/user credentials, explicit per-app principal and audience ACL, narrowly granted service capabilities, secret broker, network/filesystem restrictions, CPU/memory/time quotas, output validation, immutable version/hash, human publication approval, execution audit, expiry and revocation. Opening a shared app must not confer access to its private build context. No execution or deployment UI/API is implemented in this slice.


## Northstar negotiation revision
Preserve the current SQLite visibility gateway, immutable events, demo bearer sessions, model-call logging/retry wrapper, and legacy services/tests. Replace the demo entry UI with exactly three Slack-style channels: Business private, Technical private, shared collaboration. Hide the old dashboard from entry routes; retain its implementation internally until the new slice is validated. No live connectors are used for this fictional scenario.

Import only team_b/team_t and an explicit public-field scenario allowlist. QA reference and evaluation-only discovery are not runtime fixtures. Stable external source IDs map to immutable run-prefixed event IDs; reset creates a new run, preserving old audit events. Business uses bit 2, Technical bit 1 with dedicated demo principals and one agent each. Every source read and agent prompt is restricted to the active run and authenticated clearance. Notification metadata is rendered as chat history; fictional URLs are never external links.

Store topics/drafts/publications/votes as existing append-only events; draft disposition uses the existing releases table. No second database or generic artifact abstraction. Private prompts include at most twelve authorized evidence records plus approved shared proposals. Structured LLM outputs must cite only retrieved source IDs and exact substring excerpts. Candidate quotes are unchecked by default and stay private. Publishing takes selected IDs, never arbitrary quote text, binds the exact server-rendered preview hash, validates ownership and exact substrings again, and creates a private approval audit plus independent shared publication. Shared publication refs point only to the private audit (not raw private chunks); recipients see selected quote provenance but raw citation routes remain protected.

The new prompt intentionally replaces the earlier blanket date-placeholder policy for this scenario: source-supported dates may appear in reviewed proposals, always marked PROPOSED, never committed automatically. Unsupported dates/financial/internal claims and verbatim private quotations in argument prose are blocked. A final decision is human-authored from shared discussion, exact-hash approved separately by each team, and conditional by default. Unresolved conditions prevent a committed status. Human shared posts are distinct, visibly audience-confirmed actions. Show at most three agent publications, then request a joint decision. Offline mode is explicitly a deterministic evidence-selection simulation, not autonomous negotiation.

### Completed negotiation slice and regression findings
The entry UI now exposes only the three channels, local source details and review/decision modals. The previous dashboard module is archived and unimported. Negotiation tokens are rejected by legacy API wrappers, preventing inherited operator exchanges. The negotiation shared snapshot excludes all private sources/drafts, even those belonging to the viewing team; private review requests remain scoped separately. SSE sends content-free refresh notifications; periodic snapshots provide a fallback. Source display uses stable fixture IDs, run-specific internal IDs and imported author/timestamps. Sources withdrawn by the visibility gateway are excluded from new context.

Fresh-process browser testing caught an ordering defect: the legacy seed migration retired the newly imported negotiation run on an empty database. Startup now seeds only the new scenario; legacy regression tests seed their own independent data. A child-process test checks a genuinely fresh server, not just service calls in an already seeded test database. Reset seeds only the new fictional scenario and never queries live connectors.

The real provider path is implemented with the existing forced structured-response wrapper and server validation, but no key was available. SDK mock tests validate scoped prompts, changed inputs after CSV evidence removal, and rejection of invented quotations. They do not verify live-model reasoning sensitivity (acceptance criterion 11); that remains an explicit live evaluation task. The standalone browser rehearsal uses an isolated memory database, verifies the complete offline review/publish/decision choreography, and never changes the active demo database.

## Three-team evidence handoff revision
The latest requirements supersede the Northstar negotiation as the primary UI. Preserve its implementation and tests, and reuse the original knowledge-answer generator, bitmask gateway, SQLite events/releases/questions, validation, Anthropic wrapper and human authority checks. Build a focused single-screen Sales/Engineering/Infrastructure demo with deterministic rate-limit fixtures and no live connector dependency. Infrastructure adds bit 4; identities have one team bit, never combined clearance. Its human is read-only; reading does not confer release authority.

The existing core.approve atomically approved and released text, so it cannot demonstrate an edit invalidating a pending approval. The new handoff service separates save revision -> approve exact hash -> release approved hash. Edits append a new immutable private draft, reset approval state/approver and change the hash; the old approval remains in append-only history but cannot authorize the new revision. Final release reuses core.approve inside a transaction after checking the separate approval and resetting only the staged row temporarily. Shared artifacts use an explicit metadata allowlist: approved text, public artifact identity/hash, approver and timestamp, with no private source refs/reasoning exposed in application responses.

Security scenarios use isolated, deterministic fixture channels in the same store, run actual scoped retrieval/generation/authorization/transition assertions, return only sanitized check results, and retire their scratch records afterward. They do not mutate the live demo or change global model configuration. An optional server-only force-rules parameter keeps these scoped checks reproducible even when interactive LLM mode is configured. This checks deterministic enforcement, not live-model prompt-injection robustness. A failure must render as a failure, never a precomputed passing badge. No private canary/source text is included in scenario reports. No new dependencies or database.

### Implemented checks and refinements
The main rate-limit response cites the actual shared documentation and PR #412. Source projections expose owner/type/status/policy; released projections intentionally omit private audit refs and model context. Engineering revisions keep an authorized, append-only hash/history view. Sales and Infrastructure return no private draft records before loading draft contents. Invalidated approvals are rejected through HTTP as well as services; legacy APIs reject current demo tokens so the old atomic approval route cannot bypass the new two-phase lifecycle.

Rate-limit conflicts (different requests/minute values) and explicitly stale/expired source states downgrade an answer to escalation/uncertainty. This is a narrow, tested conflict detector, not a general semantic contradiction resolver. Unknown/forbidden source IDs both return 404. Validation errors show field/code only, and default error logs show sanitized status categories rather than raw untrusted/model values.

Browser rehearsal exposed a scope bug in the inherited outbound scanner: fingerprints in old private transcript copies from unrelated runs could block a safe repeated approval test after a live release. Added an optional channel filter in the visibility gateway/scanner, preserving old callers' default behavior. The new flow scans the active workspace only; repeat-run tests cover prior released/retired scratch records. The UI displayed the real failed check before the fix, and fault-injection regression verifies failures cannot become passing badges. Runner results are cleared when a rerun starts so stale passing results do not survive an error.

The current UI refreshes authorized snapshots by short polling. Mode defaults to deterministic rules unless configured otherwise. Live generation remains behind the existing structured service/provider adapter; no API key was available, so live reasoning and injection resilience are unverified. The older Northstar service/tests are preserved, but its UI/rehearsal are archived rather than advertised as the primary experience. No new dependencies.
